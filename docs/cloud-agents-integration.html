Cloud Agents Integration — Lightspeed Stack

Two independent growth axes on the same integration — go deeper on capability, go wider on isolation. Teams start at the top-left corner with zero infra, and move outward only as their needs mature.

Build on the same lightspeed-stack integration at every point on both axes — teams can start experimenting with zero infra, then grow deeper (capability) and wider (isolation) independently, without rewriting a single workflow.

Everything here reduces to one atomic unit — the agent run — declared once as data, not code. A workflow is just several of them, composed.

One building block, two levels of composition — a single agent run for a single-shot task, or several chained into a workflow for a multi-step task. Where each one executes (in-process, sub-process, sandbox) is a separate, orthogonal choice — see Tabs 1–3.

POST /v1/agents/run, spawn: "none" — the agent runs in-process. Same agent loop (LLM + MCP tools + skills) used by every spawn mode.

Same request, same agent loop, same output shape — POST /v1/agents/run, spawn: "ephemeral". The difference is entirely underneath: a gateway-mediated, hardened sandbox instead of the API process.

POST /v1/workflows/run — a workflow is a graph of steps, and each step is exactly the single-agent-invocation from Tab 2. The workflow runner owns sequencing, context-passing, and approval gates; it does not re-implement the agent loop.
